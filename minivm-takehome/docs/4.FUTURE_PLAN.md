# What I would do with a few days and unlimited compute and tokens

## 1. The goal

**Optimize programs so they run faster on data we've never seen, and never give a wrong answer.**

Two measurable targets:

| Target | Today | Goal |
|---|---|---|
| Held-out cycles ratio (geomean; lower is faster) | 0.602 (10/10 correct), but 3 of 10 cases are now burnt, so the honest number is pending a refreshed set | **under 0.5**, on a freshly rebuilt held-out set, with 10/10 correct |
| Known tricks and traps caught by the evaluator | 44/44 planted bugs caught, 0/17 false alarms; 10/10 held-out traps flagged, 0/10 false alarms (last recorded run) | **100% caught, always**, as the trap list grows, with 0 false alarms |

**The strategy in one line:** make the evaluator strong first, then stronger. A strong evaluator makes the optimizer easier to build, because every new rule can be tried quickly and safely. A weak evaluator makes every rule a gamble.

## 2. Open question for the team: precision or recall?

- **Precision** means "when we do optimize, we're right". The optimizer only rewrites what it can prove safe, and prints the input unchanged on any doubt.
- **Recall** means "we optimize every program we could". More rewrites fire, which gets closer to the best possible speedup but takes more risk.

**So far we have optimized for precision.** Every rule is guarded, the cost check rejects marginal rewrites, and the fallback prints the original. The result is 0 wrong answers everywhere, with some speed left on the table: three held-out cases scored 1.000 until we added rules for them.

We should **confirm with the team which matters more**. If wrong answers are unacceptable, which is our assumption because a single defect fails the run, we keep precision first. Recall then grows only as fast as the evaluator can prove new rules safe, which is another reason to put the evaluator first.

## 3. Where things stand

- **Optimizer** (`optimizer/`): 11 rules. It reads the program, gives every register a unique name, applies the guarded rewrites, keeps the result only if the price list says it's cheaper, and prints the input unchanged on any doubt.
  - Suite speedup 1.52×; `./evaluate` speedup 2.12–2.56× (seeds 1–3); 0 wrong answers (`3.PROGRESS.md`).
- **Evaluator** (`evaluator/`, `./evaluate`): makes random but legal tables and programs, runs the original and the optimized program, and compares the answers by type, order and ties.
  - Meta-eval: 44/44 planted bugs caught, 0/17 false alarms (`tests/runs/meta_report.md`).
- **Held-out check** (10 trap cases built outside the build sessions; not in this package): 10/10 correct, ratio 0.730 → 0.602 after rules 9–11. Cases 01, 03 and 06 were studied to get there, so they're burnt and now in `tests/regressions/`.

**Lessons so far:**
- Correctness holds because every rule ships with guards and a buggy twin.
- The remaining speed is in rules that handle NULLs carefully, in rewrites that span several instructions, and in join order.
- The evaluator once missed a buggy twin because no test program had the right shape. Gaps in what the evaluator generates are the biggest risk, so closing them comes first.

## 4. Priorities, in order

Each theme builds on the one before it. The evaluator work (A and B) comes first, because it makes the optimizer work (C and D) faster and safer.

### Priority A: make the evaluator see everything (it must catch 100% of known traps)

1. **Turn every known trap into a permanent test.** Every trap we know about becomes a fake optimizer in `tools/fakes.py` and a program in `tests/regressions/`. Sources: the `1.BUILD_PLAN.md` safety rules, the held-out cases, and every buggy twin. The merge rule is that 100% of them are caught.
2. **Data that aims at the gaps (coverage-guided).** Write a small Python version of MiniVM, checked against `bin/minivm` (today `evaluator/vm.py` only runs the binary). Use it to record which tricky situations each dataset reaches: NULL inputs per instruction, empty groups, ties at a cut-off, NULL join keys, divide by zero, `''` vs `'  '`, Unicode, values at check bounds. Then generate data and programs aimed at whatever nothing has reached yet. This closes the kind of gap that let `b_isnull_two_ops` slip through at first.
3. **Golden-style traps.** More cases like the held-out set: friendly data where the trap passes, tricky data where it fails, a control dataset, a wrong rewrite that must be flagged, and a correct rewrite that must pass.
4. **Never pass without earning it.** A timeout, a crash in `bin/minivm`, or a skipped dataset gives "incomplete" with a non-zero exit code, never "pass".

### Priority B: make the evaluator keep getting stronger on its own

1. **An automated red team.** A separate agent reads the docs and the rule list and writes believable but wrong optimizers. Any one that slips past the evaluator shows a hole: we shrink it to the smallest example, fix the evaluator, and keep the fake as a permanent test.
2. **Nightly runs at scale.** Every night, run thousands of seeds over the suite, all traps and the meta-eval, plus the stress cases (section 5). Each failure is shrunk automatically, and a report tracks over time:
   - wrong answers;
   - speedup;
   - coverage;
   - red-team catch rate;
   - how often the optimizer falls back.
3. **A held-out set that stays honest.** It's run only at checkpoints, and the agents building rules never see it. Once a case is studied, it's burnt: it moves into the public tests, and a fresh agent with no memory of the build writes a replacement for the same kind of trap.

### Priority C: let the optimizer find more speed, safely (toward held-out under 0.5)

With A and B in place, each item here is a quick try-and-check loop.

1. **Choose the join order by cost, and say why.** Try the possible join orders, price each one, and pick the cheapest. A short note in a side file explains the choice, e.g. "filter `lines` first: 86 → 12 rows before the join, saves ~1,400 cycles". This is likely the biggest remaining gain on multi-join programs.
2. **More rules, each with its buggy twin.** The evaluator must pass the rule and catch the twin, or the rule doesn't go in. Next rules:
   - push unused columns out before joins;
   - remove a join only when keys and refs prove it's safe;
   - more NULL-aware filter simplification;
   - more multi-instruction idioms like the self-join rewrite.
3. **Let all rewrites compete at once.** Today the rules run in order, so an early rule can block a better one later. Keep every equal version of the program the rules produce and pick the cheapest at the end (an "e-graph"), with a time limit and the existing fallback.
4. **A real price list.** Fit the cost model to cycles measured with `bin/minivm` on thousands of programs, so "is this cheaper?" uses real numbers and good rewrites aren't refused.

### Priority D: the optimizer checks its own work

Before printing, the optimizer checks its output against the input in two ways:
- a solver proof for the parts it can model (three-valued logic, NULL propagation, typed comparisons);
- a quick run on small tricky tables (all NULL, empty, duplicate keys, edge values).

If either fails, only that rewrite is dropped. This is a second safety net behind the evaluator, which lets recall grow without giving up precision.

## 5. Always-on checks

These run with every change and every night. They support the priorities above rather than competing with them.

### Extreme scale tests

`1.BUILD_PLAN.md` calls for near-limit stress cases, kept out of the normal test run:
- **Very long programs:** programs near the instruction limit (20k+ lines). The optimizer must finish within its time limit (under 1 s) or fall back cleanly; today the 20k-line program takes 0.57 s.
- **Big tables:** row counts near the VM's limits, to check rewrites don't push a program over the work limit. For example, a nested-loop join gives the same answer as a hash join but can blow the limit.
- **Many registers:** programs that use a very large number of registers at once.
- **Worst-case fan-out:** joins and groups where one key matches huge numbers of rows (e.g. the ~4M-pair self-join in `tests/stress/`).
- **Evaluator under load:** a full run still finishes within its 2-minute budget at these sizes, and its watchdog stops a stuck run.

Each case records size, optimizer time, cycles before and after, and whether it fell back.

### Cost analysis

- **Cycles:** how many cycles each rule saves, per program. Rules that save almost nothing get removed to keep the optimizer simple.
- **Optimizer time:** time per pass on small, normal and huge programs, to see which rules get slow as programs grow.
- **Evaluator time:** time per check, so the 2-minute budget is spent where bugs are most likely.
- **AI spend:** credits per phase and per agent, from Snowflake's Cortex Code usage history (see `AI_USAGE.md` at the repo root). Planning used extra-high thinking where medium would have done, so next time thinking effort is set per task: high only for hard reasoning, medium or low for routine work.

### Failure-mode tests and graceful exits

Each failure from `1.BUILD_PLAN.md` §10 gets a test that must keep passing and a planned graceful exit, so the tools never hand back a wrong answer or hang.

| What can go wrong | Test that catches it | Graceful exit |
|---|---|---|
| A rewrite breaks NULL handling | NULL-heavy data and NULL-bug fakes | The self-check fails, so that one rewrite is dropped and the rest are kept |
| A rewrite adds an error (e.g. divide by zero) | fakes that move a division above its filter | The rewrite is dropped; if unsure, print the input unchanged |
| Row order or ties get lost | order- and tie-aware comparison, and fakes that reverse or drop tie-breakers | Keep the original sort keys; drop the rewrite |
| The evaluator is too lenient | the planted-bug fakes must all be caught | Block merges until the missed fake is caught again |
| The evaluator is too strict | the honest fakes must all pass | Report the dispute with the smallest example instead of failing silently; a person decides |
| Types get confused (BOOL vs INT, 1.0 vs 1.00) | strict typed comparison tests | Treat any type mismatch as a difference (never "close enough") |
| Stats get used for correctness | data that deliberately breaks the stats | Rules may read stats only for cost; a lint check rejects any other use |
| A rewrite blows the VM work limit | near-limit stress cases | The cost check rejects it; if unsure, keep the original join or loop |
| The optimizer is too slow on huge programs | 20k-line stress programs with a time limit | At the deadline, stop and print the best checked program so far, or the input |
| The evaluator runs past 2 minutes | wall time in every report, plus a watchdog | The watchdog stops the run, reports what was checked so far, and marks the result "incomplete", never "pass" |
| Overfitting to known programs | held-out generated programs and the rotating held-out set | Rules that only help known programs are not merged |
| The same bug in both optimizer and evaluator | separate code, and a check that they share none | Fail the build if shared code is found |

**Exit rules that apply everywhere:**
- **The optimizer always prints a valid program.** On any crash, bad input, missed deadline or failed self-check, it prints the input unchanged and exits 0. Slower is fine; wrong is not.
- **Drop the smallest piece first.** If one rewrite fails its check, only that rewrite is dropped.
- **The evaluator never reports a pass it didn't earn** (see A.4).
- **Save the evidence.** Every fallback or incomplete run writes a small log (which rule, which program, why), so the nightly report can count them.
- **Agents stop instead of guessing.** If an agent can't tell from the docs whether a rule is safe, it leaves the rule out and raises the question with a person.

## 6. How the work runs: three loops

1. **Evaluator against the validation set (keep this loop green before all others).** The evaluator must catch every buggy fake (every rule's twin, every trap, every red-team fake) and pass every honest one. If it misses bugs, loop 2 means nothing.
2. **Optimizer against evaluator.** Agents build one group of rules each. Every change runs the evaluator and the traps. A wrong answer sends it back with the smallest failing example, and a pass is kept only if the speedup holds.
3. **Held-out set, rebuilt when a case is burnt.** It's run only at checkpoints, for the headline number. A fresh agent replaces every burnt case.

Fresh-context reviewer agents check each rule against the docs before it goes in.

## 7. Rules for merging a change

- 0 wrong answers on `./evaluate` (several seeds), the test suite, every trap and the stress cases.
- 100% of known traps and buggy fakes caught, including the new rule's twin; 0 false alarms on honest fakes.
- The self-check is on and falls back cleanly.
- No test group gets slower; the optimizer stays within its time limit.
- One commit per rule, with a plain-English row in `3.PROGRESS.md`.

## 8. Milestones

| Milestone | Done when |
|---|---|
| M1: evaluator sees every known trap | every known trap is a fake plus a regression program; 100% caught, 0 false alarms; "incomplete" never reads as "pass" |
| M2: evaluator improves on its own | coverage report live; red team and nightly runs running; every miss turns into a permanent test |
| M3: fresh held-out set | burnt cases replaced by a fresh agent; baseline re-measured honestly |
| M4: optimizer speed | join ordering, the next rules with twins, calibrated costs; held-out geomean **under 0.5** on the fresh set, 10/10 correct |
| M5: second safety net | self-check (solver + tricky tables) inside the optimizer; recall can grow without giving up precision |

## What I would not do

- Hard-code answers for known programs. It would raise the held-out score but prove nothing about new programs.
- Use table stats for anything but cost. Stats describe friendly data, and the traps show that rules relying on them break on legal data.
- Trade precision for recall without the team's agreement. One wrong answer fails the run.
