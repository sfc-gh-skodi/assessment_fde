What we learned

  1. Small files beat one big answer. The optimizer subagent died at its output limit. Writing 5 modules of 70–220 lines each worked first time.
  2. The fallback guard can hide bugs. A string literal with a space (' / ') was read as a sort key, crashing 6 programs into the "print the original" path. The evaluator still said 0 defects; only a per-stage smoke test exposed it.
  3. Measure before building. Before extending rank 1, a 0.1 s scan showed nothing left to win: dead-code removal already deletes 47% of instructions on generated programs, and CSE only 31 of 1,290.
  4. Machine time is cheap; LLM time dominates. A full 3-seed gate costs ~90 s. A coding round costs minutes of model time, so a script digest (~1k tokens per round) matters more than skipping tests.
  5. Generated programs and random schemas are what keep the optimizer honest. The 8 examples alone would let name-matching or overfit rewrites pass.
  6. Our own tooling has bugs too. The evaluator wrote helper files into the corpus, and an instrumented original crashed on an empty GALL. Both were caught because results were checked against expectations, not assumed.

What we learned

  1. A correct rewrite can still lose. Gather composition first made the examples slower, because it also fired when the inner GATHER was still needed. Firing only when the old work dies fixed it.
  2. The fallback guard hides crashes again. Rule 2's first version threw an IndexError on every program. The loop still said 0 defects; only the speedup dropping to 1.00× gave it away. Watch the speedup, not just the defect count.
  3. "At most once" is about cost, not correctness. Element-wise work is correct after any index, but through a join that repeats rows it would be done more times, not fewer.
  4. Order-free totals need consistent shuffles. Dropping a SORT before GSUM is safe only if every column it touches is shuffled the same way; mixing with an unsorted column, or GMIN/GMAX (first of equals), would change answers.
  5. Schema constraints, not stats. Rule 3 relies only on the sorted constraint, which every table set must obey; stats only choose between correct options (rule 2 cost check, NLJOIN→HJOIN).

What we learned

  1. Memory and speed fixes can fight. Register reuse added a re-read check and pushed the 20k program to 0.66 s. Running cheap clean-up first (20,000 → 4,896 instructions before the analysis rules run) more than paid it back.
  2. Pass order matters. Lookup joins made 8 programs 1–3% slower when they ran early, because they removed the pattern filter pushdown matches on. A second phase, after everything else settles, turned that into 6 better / 0 worse. Comparing per-program cycles with and without the rule is what exposed it; the tier geomean only moved by 0.01.
  3. Moving work can add crashes. Below a SORT a filter sees the same rows, so anything can move. Below a join it sees rows the join would have dropped, so only predicates that provably can't error may move, and only types we are sure of (stored columns) count.
  4. Constraints decide, stats price. Lookup joins and range folds use only refs, key, not_null and check, which every table set must obey. Stats only choose between correct versions.
  5. A held-out set keeps us honest. The golden set never fed the rules; it only confirmed 10/10 after each step, and its ratio moved only when general rules (range folds, TOPK) applied.
